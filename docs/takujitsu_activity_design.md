## 1. 擇日象意.pdf 37ページの構造解析

### 1.1 全体構成

PyMuPDFで37ページ全件を確認した（画像PDF＋OCRテキスト層。単純な
テキスト抽出だけで判断せず、座標抽出で行・列レイアウトを検証した）。

- ページ0〜35（36ページ）：本体の表。**12ヶ月×3ページ＝36ページ**
  という規則的な構成を確認した（正月=p.0-2、二月=p.3-5、……、
  十二月=p.33-35）。
- ページ36（最終ページ）：十二月の残り2行（壬戌日・癸亥日）＋書誌情報
  （書名『擇日天文學』、著者「鐡筆子」、出版社「竹林印書局」、
  2009年7月初版）。用事データではなく奥付ページ。

各月3ページ×60干支＝1ヶ月あたり60行、12ヶ月で720行が本来の総行数と
推定される（1ページあたり平均20行）。

### 1.2 レイアウトの向き（重要な発見）

座標抽出（`get_text("words")`）でx/y座標を確認したところ、本文は
**縦書き・右から左に読む伝統的な組版**であることを確認した（例：ページ0
の見出し行は x=409(憲)→379(協)→347(集)→318(宜) と右から左に並んでおり、
読み順は「憲協集宜」となる）。PyMuPDFの`get_text()`（フラットテキスト
モード）は概ね正しい読み順で文字列を返しているため、今回の解析は
フラットテキスト抽出＋座標抽出の併用で行った。

### 1.3 各ページのヘッダー

各ページ最上部に「憲協集宜」という4文字の柱（ランニングタイトル）が
配置されている。これは**「憲書」と「協紀[辨方書]」の宜（吉用事）情報を
集めた表」であることを示すタイトルと判断した**（本文中に「憲」「協」の
出典を明示的に定義した一文は無いが、後述1.5節のとおり表の構造・
本文全体の文脈からこの理解が最も整合する）。ページ左端には元の書籍の
通し頁番号（例：四九六＝496）が漢数字で印字されている（本アプリの
擇日データとは無関係の書誌情報）。

### 1.4 1行の構造

各行は次の形式に従う（OCR起因の文字化けを除いた理想形）。

```
[月label]
[六十干支]日【憲宜】[用事の並び（0件の場合あり）]【協紀】[仝／全／俱不取／加+追加用事の並び]
```

例（ページ0、丙寅日の実際の記載。読みやすく整形）：

```
丙寅日
【憲宜】會親友 結婚姻 裁衣 豎柱上樑 立券交易 納財 牧養 安葬 啓攢
【協紀】加 納采問名 解除 開倉庫出貨財 納畜
```

### 1.5 「憲宜」「協紀」の関係（今回の最重要確認事項）

擇日象意.pdf全体を確認した結果、【協紀】欄には常に以下いずれかの
パターンしか出現しないことを確認した（頻度は636行の解析ベース）。

| パターン | 意味 | 出現例 |
|---|---|---|
| `加` ＋ 用事の並び | 【憲宜】のリストに**追加**する用事がある | 「【協紀】加 祈福 求嗣 臨政親民 納采問名 解除…」 |
| `仝` または `全` | 【憲宜】と**全く同じ**（協紀からの追加無し） | 「【憲宜】祭祀 上表章 會親友…【協紀】仝」 |
| `俱不取` | 【憲宜】【協紀】**双方とも**使える用事が無い | 「【憲宜】【協紀】俱不取」 |

**結論：憲宜と協紀は単純な重複でも、独立した別評価でもない。「協紀」欄は
常に「憲宜のリストに対する追加分（加）」「憲宜と同一（仝/全）」
「両方とも無し（俱不取）」のいずれかであり、憲書（憲宜側）を基本とし、
協紀辨方書（協紀側）が追加の宜を補う、という補完関係にあると判断した。**
（本文にこの関係を明示する説明文は無いため、上記は表の構造そのものから
確認した事実であり、一般知識による解釈を加えたものではない。）

このため、データ設計上は
- `ken.activities`（憲宜のリスト。0件の場合あり）
- `xieji.mode`（`"additional"` | `"same"` | `"none"`）
- `xieji.additionalActivities`（`mode === "additional"` のときのみ）

を別フィールドとして保持し、**「その日に成立する宜の全体集合」は
`ken.activities ∪ (mode==="additional" ? additionalActivities : mode==="same" ? ken.activities : [])`
という計算式で導出可能にする**（3.2節）。憲宜・協紀のどちらの情報かという
出典（source）を失わない設計とする。最終表示で両者を統合済みの1リストと
して見せるかどうかは、この設計とは別にUI側で決めてよい。

### 1.6 宜／忌の記載方式

擇日象意.pdf全体（見つかった約636〜720行相当）を確認したが、
**「忌」という文字は文書中に一度も出現しなかった**（`grep`で0件を確認）。
【憲宜】【協紀】のいずれも「宜（推奨される用事）」の情報のみを記載して
おり、「忌（避けるべき用事）」を直接記載する欄・表は存在しない。

**結論：擇日象意.pdfは「宜」専用の資料である。「宜に書かれていない
用事＝忌」という仮定は本文のどこにも根拠が無く、採用しない**（ユーザー
指示のとおり）。凶用事（忌）をどう導出するかは、別の情報源（既存の
凶神occurrence・resolution結果、または擇日象意.pdfの範囲外にある同書の
別の章）に委ねる必要がある。これは4章・6章で扱う「将来の統合」課題として
持ち越す。

## 2. 用途判定のキーの特定

### 2.1 一意に行を取得するためのキー

各行は「月（正月〜十二月）」×「六十干支（甲子〜癸亥）」の組み合わせで
一意に識別できる。擇日実例.pdf・擇日テキスト.pdfの既存の吉神・凶神表と
**まったく同じ構造**（月×60干支＝720通りの参照表）であることを、
1.1節の3ページ/月という構成、および行の中身（干支＋活動名のみで、
実際の年月日情報が一切登場しない）から確認した。

具体的なキーは以下のとおり：

- `monthBranch`（月令）＝ 「正月」等の月labelを標準対応（正=寅、二=卯…）
  で変換した値
- `dayStem` + `dayBranch`（または `dayGanzhi`）＝ 行の六十干支

`lunarMonth`・`yearBranch`・十二建除・二十八宿等は擇日象意.pdfの行を
特定するためには不要（表自体がこれらの情報を一切使っていない）。

### 2.2 「月」はmonthBranchかlunarMonthか

**結論：monthBranch（月令）である。lunarMonthではない。**

根拠：

1. 擇日象意.pdfには実際の年月日・農暦月番号・「閏」「農暦」「陰暦」
   「月建」「節」といった暦法を示す語が**一度も出現しない**（本文検索で
   確認済み）。特定の年に紐づいた実カレンダーではなく、擇日実例.pdfと
   同様の**抽象的な参照表**である。
2. 各月とも例外なく60行（六十干支の全パターン）を持ち、実際の暦月の
   日数（29日/30日）とは無関係な行数になっている。これは「正月＝寅月」
   のような節月支ベースの抽象表でのみ成立する構造で、実際の農暦月
   （29〜30日）を表すものではあり得ない。
3. これは既存の擇日実例.pdf・凶神歸忌（16番、孟月＝正・四・七・十月→
   丑日）等ですでに確立した「序数の月ラベルはmonthBranchの標準対応
   （正=寅、二=卯……）を指す」という設計原則（docs/takujitsu_decisions.md
   参照）と完全に整合する。

したがって、**monthBranchとlunarMonthを混同しない**という既存の設計
原則をそのまま維持し、擇日象意.pdfの「月」もmonthBranchとして扱う。

### 3.3 OCR起因の文字化けについて

擇日象意.pdfは画像PDFのため、特に「豎柱上樑」（12種類以上の異なる
誤字パターンを確認：上揆・上採・上櫟・上棵・上模・上擦・上燦・上探・
上概等）、「安碓磑」（安礁磑・安確磑・安礁礎・安確礎等）、「憲宜」
（意宜・惠宜・宣宜等）、六十干支そのもの（王←壬、已←巳、西←酉等）
に多数の文字化けパターンを確認した。今回は文脈から元の用語を復元できた
ものはすべて正しい用事に集約したが、**実装フェーズで実データを確定する
際は、擇日テキスト.pdf作業時と同様に高倍率画像確認（PyMuPDFの
`get_pixmap`）による裏取りを必須とする**（推測での確定を避けるため）。

## 4. 推奨する用事ID・データ構造

### 4.1 ID設計方針

用事便覧側の現代語や、`marriage`/`construction`のような英語の大分類を
IDにはしない。**擇日象意.pdf自身に印字されている原語（漢字表記）を
そのままIDとする**方針を提案する。これは、本プロジェクトの吉神・凶神
occurrence名がすべて`"天徳"`・`"六合"`のような原語文字列そのものを
キーとして使ってきた既存の設計慣習（`src/lib/takujitsu/shinsatsu/*.ts`）
と一貫しており、新しい命名規則を持ち込まない。

異体字（3.2節Aの11件）は、擇日象意.pdf側の表記を正規のIDとして採用し、
用事便覧側の表記は`aliasNames`に保持する（どちらを正規にするかは
恣意的だが、判定テーブルの母体である擇日象意.pdf側を優先する）。

### 4.2 型定義案

```ts

interface ActivityDefinition {
  /** 安定的な内部ID。擇日象意.pdfの原語表記そのもの（例："祭祀"）。 */
  id: string;
  /** 擇日象意.pdfに実際に印字されている表記。通常はidと同じ。 */
  originalName: string;
  /** 他資料での異表記（新字体/旧字体・類似語候補）。id と同一視できると
   *  判断したものだけを入れる（3.2節Aの異体字11件はここに入れてよい。
   *  B分類の3件は「同一とはまだ判断していない」ため、別途
   *  `relatedCandidates` のような未確定候補として持たせる案も検討）。 */
  aliasNames?: string[];
  /** 用事便覧.pdfとの対応状況。 */
  reference?: {
    /** 用事便覧.pdfの通し番号。 */
    entryNo: number;
    /** 一致度。 */
    matchConfidence: "exact" | "variant" | "similar" | "none";
    /** 用事便覧.pdfのふりがな付き見出し（現代語）。 */
    modernName: string;
    /** 用事便覧.pdfの説明文。 */
    modernDescription: string;
    /** 用事便覧.pdfの篇（祭祀篇・生活篇・婚姻篇・建築篇・工商編・
     *  農林漁業編・喪葬編）。 */
    category?: string;
    /** B分類（similar）の場合、確認事項の要約。 */
    note?: string;
  };
}

  dayBranch: string;

    activityIds: string[];

  xieji: {
    mode: XiejiMode;
    /** mode === "additional" のときのみ、憲宜に対する追加分。 */
```

```ts
/** その行で「宜」となる用事の全体集合（憲宜と協紀を統合した見解）。
 *  出典を区別したい場合は ken/xieji を個別に参照する。 */
function resolveKenYi(row: ZeyiShogiRow): string[] {
  const base = row.ken.activityIds;
  if (row.xieji.mode === "additional") {
    return [...new Set([...base, ...(row.xieji.additionalActivityIds ?? [])])];
  }
  if (row.xieji.mode === "same") return base;
  return base; // "none" の場合も憲宜自体は独立して存在しうるためbaseを返す
  // （憲宜側にすでに活動がある「俱不取」以外のケースを想定。実際には
  // 「俱不取」は憲宜側も空集合になる観測結果のため、通常は空配列になる）
}
```

### 4.3 なぜこの構造か

- 用事名を判定キーにせず`id`で扱うことで、将来もし原語の表記ゆれが
  複数見つかっても`aliasNames`に追加するだけで済み、既存の判定ロジック
  （`id`を参照する箇所）を変更しなくてよい。
- `ken`/`xieji`を分離することで、1.5節で確認した「協紀は憲宜への追加分」
  という関係を失わずに保持できる。将来、憲宜のみ・協紀のみを別々に
  重視する実装判断（例：憲宜を優先、協紀は参考情報扱いにする等）が
  必要になっても対応できる。
- `reference`フィールドで用事便覧との対応関係・一致度を明示すること
  で、B分類（類似語・要確認）のデータをうっかり断定的に扱ってしまう
  ことを防ぐ。

## 5. No.10（大時・天吏）「攻めのビジネス」との対応調査

`docs/takujitsu_resolution_rules.md`のルールNo.10（大時・天吏、reduced）
には、本文（擇日テキスト.pdf p.22）の「徳合・天赦にて解除するが攻めで
あるビジネスは凶。」という用途限定の注記がある。この「攻めのビジネス」
に対応する用事が、今回抽出した50種の用事（擇日象意.pdf）または用事便覧
93項目のいずれかに存在するかを調査した。

**結論：対応する用事は見つからなかった。** 擇日テキスト.pdf自身の
該当項目（11番大時・天吏）の象意・忌リスト（「城を攻めるのを忌む日」
「忌：出軍、増改築、會親友、臨官、赴任、遠行、訴訟」）に含まれる
「出軍」（軍を出す）「訴訟」（裁判）に相当する用事は、擇日象意.pdf・
用事便覧.pdfのどちらの語彙にも存在しない（用事便覧は民生・建築・
商業・農林漁業・喪葬関連の活動が中心で、軍事・訴訟系の項目を持たない）。

したがって、「攻めのビジネス」に対する`reduced`の用途限定情報は、
**今回抽出した用事マスタでは表現できない**。この対応付けは推測で行わず、
`docs/takujitsu_resolution_rules.md`のNo.10の記述（自由文字列の`note`）
をそのまま保持し、将来、軍事・訴訟系の用事情報を含む別資料が見つかった
場合に再検討する、という結論をここに記録する。
