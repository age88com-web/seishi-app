## 2. 最重要原則（今回の棚卸しで徹底した点）

- 「神殺が吉だから全用途に吉」「凶神だから全用途に凶」とはしない。
  本文に明記された具体的な用事だけを拾う。他用途への一般化はしない。
- 本文から確定できない対応付け（同じページに複数の象意パラグラフが
  並んでいて、どの項目に属するか一意に決まらない等）は「保留」として
  明記し、推測で埋めない。
- 原典用事名（擇日テキスト.pdfの表現）と用事便覧の現代語訳は別フィールドとして
  保持し、判定ロジック上で混同しない。
- 解除・相殺・増悪の条件そのものは `docs/takujitsu_resolution_rules.md` に
  既にまとまっているため、本ドキュメントでは重複記載しない（用途限定の
  残存条件、例えばNo.10大時・天吏の「攻めのビジネスは凶のまま」のような
  ものだけをここで扱う）。

## 8. resolutionとの関係（用途判定レイヤーでの扱い）

`docs/takujitsu_resolution_rules.md` の分類方針をそのまま踏襲する。

- **cancelled**（解除された凶神）：その凶神由来の「忌む用事」を最終用途
  判定に反映しない。
- **aggravated**（増悪）：元の忌む用事を維持し、増悪した事実を保持する
  （用途ごとの重み付けは今回は設計しない。本文に優先順位の記載が無い

- **active/pending**：忌む用事をそのまま反映する（pendingは解除条件が
  未確定なだけで、忌む用事自体の存在は本文から確定しているため）。

### 9.2 用途ごとの最終評価（相殺しない設計）

ユーザー指示のとおり、「吉要素あり」かつ「凶要素あり」の場合に勝手に
相殺しない。用途ごとに positive/negative の出典を両方保持する。

```ts
interface ActivityEvaluation {
  /** 用事名（原典の用語）。 */
  activity: string;
  /** この用事を「宜」とした神殺・暦注の一覧（出典を失わない）。 */
  positiveSources: { name: string; category: ShinsatsuActivityProfile["category"]; status: string }[];
  /** この用事を「忌」とした神殺・暦注の一覧。 */
  negativeSources: { name: string; category: ShinsatsuActivityProfile["category"]; status: string }[];
  /**
   * 最終評価。本文に優先規則が無いため、positiveSources と
   * negativeSources が両方非空の場合は独自の優先順位をつけず "mixed" とする。
   */
  verdict: "good" | "bad" | "mixed" | "neutral" | "pending";
}
```

- `verdict` の決定：`positive非空 && negative非空` → `"mixed"`、
  `positiveのみ非空` → `"good"`、`negativeのみ非空` → `"bad"`、
  どちらも空 → `"neutral"`、いずれかの出典が `pending` 状態の神殺のみ
  → `"pending"`（本文由来の情報が確定していないため）。
- 独自の優先順位（例：「凶が1つでもあれば強制的にbad」等）は、
  ユーザー指示「本文に優先規則がない場合は独自の優先順位を作らない」
  に従い、今回は設計に含めない。将来、本文に優先規則の記載が
  見つかった場合にのみ追加する。

### 9.3 なぜこの構造か

- `ken`/`xieji`のような擇日象意.pdf固有の出典分離（前フェーズの設計）
  ではなく、神殺・暦注ごとの象意を積み上げる構造にすることで、
  「その日成立した神殺・暦注から吉用事・凶用事を導出する」という
  今回の本来の目的（0章）に直接対応する。
- `positiveSources`/`negativeSources` を残すことで、UI側で「なぜこの
  用事が凶と出たか」を神殺名まで遡って表示できる（デバッグ・検証の
  両方に有用）。
- 擇日象意.pdfとの答え合わせ（10章）は、この`ActivityEvaluation`の
  `verdict`（またはpositiveSourcesのactivity集合）と、擇日象意.pdfの
  該当行（monthBranch×日干支）の宜リストを比較するだけで機械的に実行できる。

# 六黄道COMPOSITE型 原典確定フェーズでの調査結果（2026-09-09、コード変更なし）

神殺象意.pdf原本画像確認により、六黄道（青龍・明堂・寶光・玉堂・司命の
5神、金匱は対象外）が「與吉神併，則從所宜，與凶神併，則從所忌」という
COMPOSITE型（同日に成立する他の吉神・凶神の宜/忌をそのまま反映し、
単独では固定の宜忌を持たない）であることを確定した。現行の
`activityProfiles.ts`（6神とも`favorableActivityIds: ["家族会議",
"遠行"]`のLIST型データ）は、金匱についてはSUPPORTED（擇日テキスト.pdf
p.15由来）だが、5神についてはこの確定したCOMPOSITE構造とCONFLICTして
いる。

## 本番実装（2026-09-10、六黄道COMPOSITE 本番実装フェーズ）

ユーザー確定仕様：

- COMPOSITE化するのは原文列挙の5神（青龍・明堂・寶光・玉堂・司命）のみ。
  金匱はCOMPOSITE化しない。
- 5神の既存LIST型データ（家族会議・遠行）は**削除せず保持**する
  （COMPOSITEは置換ではなく追加機能）。金匱もLIST型のまま。したがって
  上記の「CONFLICT」は、5神の家族会議・遠行を**残したまま**COMPOSITE
  追従を上乗せする形で解消した（削除はしていない）。

実装：`ActivityProfile`に`composite?: boolean`を追加し5神に付与。
`evaluateActivities()`を2パス化し、第2パスで「吉神由来positive」
「凶神由来negative（resolution適用後）」だけを六黄道神自身のsourceとして
追従させる。十二建除・二十八宿・他のCOMPOSITE型神は参照しない。
指標（SOURCE VALIDATION 85.52%/68.10%、APP EVALUATION 60.47%）は
実装前後で完全に同一。詳細は
`docs/takujitsu_liuhuangdao_composite_analysis.md`14章および
`docs/takujitsu_activity_engine.md`「補足（2026-09-10）」参照。

# 十二建除「収」× 月恩／四相／時徳 → 修倉庫（2026-09-10、本番実装済み）

神殺象意.pdf 収日「宜進人口，納財，捕捉，納畜（義取諸收）。…**與『月恩』
『四相』『時德』併，宜修倉庫**」。

  ブラケット列挙＋併存語のみで共起（AND）マーカーが無いため OR（既存の

  原本画像でも「時德」直後は「併」で皆/俱/同時の語なし）。

  `buildingDay.name === "収"` かつ `resolution.kichijin` に月恩・四相・
  時徳のいずれかがあれば `{ activityId:"修倉庫", favorable:true,
  source:{ sourceType:"jianchu", sourceName:"収", note:"…と併して宜" } }`
  を1件だけ積む。「修倉庫」は収の通常 favorableActivityIds にも、月恩・
  四相・時徳の各 profile にも入れない（クロス条件としてのみ生成）。
- **保護**：occurrence（十二建除・吉神）無変更。収の常時宜（進人口・
  納財・捕捉・納畜）・季節宜（畋獵・取魚）無変更。`sourceType:"jianchu"`
  なので六黄道COMPOSITE（kichijin由来positiveのみ追従）は追従せず、
  月破の徳神抑制（`sourceType==="kichijin"` 対象）も対象外。月破が
  同日に修倉庫を忌にすれば mixed（優先順位を付けない）。
- **指標**：SOURCE VALIDATION 85.52%/68.10% 不変、APP EVALUATION 60.39%
  不変（MATCH/SHOGI_ONLY 不変。720行の収クロス16日と擇日象意.pdfの
  「修倉庫」宜日が重ならないため。一致率のためのルール調整はしない）。
  詳細は `docs/takujitsu_jianchu_seasonal_rules.md` 末尾補足。
