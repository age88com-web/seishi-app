>

## 2. 六神を一括扱いしてよいか（金匱の除外）

**結論：一括扱いできない。金匱だけ個別に扱う必要がある。**

- `docs/source/擇日テキスト.pdf`p.15の表は**12神・6黄道＋6黒道の全体**
  として金匱を含めて掲載している（p.15本文でも「青龍、明堂、天刑、
  朱雀、金匱、天徳（寶光）…」と金匱を明記）。
- 一方、`docs/source/神殺象意.pdf`の「六黄道日」を定義する文には
  **金匱が含まれていない**（「〔青龍〕〔明堂〕〔寶光〕〔玉堂〕〔司命〕
  爲六黄道日」——5神のみ）。神殺象意.pdf全7ページを通読したが、金匱に
  ついての独立した記述（COMPOSITE型・LIST型いずれの形式でも）は
  **見つからなかった**。

したがって：

- **青龍・明堂・寶光・玉堂・司命（5神）**：神殺象意.pdfが「六黄道日、
  與吉神併則從所宜、與凶神併則從所忌」と明記——COMPOSITE型の対象。
- **金匱（1神）**：神殺象意.pdfに記述が見つからず、COMPOSITE型である
  ことを原典から確認できない。擇日テキスト.pdf由来のLIST型データ
  （家族会議・遠行）のみが唯一の根拠。**金匱を5神と同じCOMPOSITE型に
  含めるのは推測になるため行わない。**

## 3. COMPOSITE型の意味の確定

神殺象意.pdfの文「與吉神併，則從所宜，與凶神併，則從所忌」を、
選択肢A〜Dで整理する：

| 選択肢 | 判定 |
|---|---|
| A. 六黄道神自身はpositive/negativeを生成しない | **原文から確認できる**（「特別な固定宜忌なし」という擇日テキスト.pdfの記述とも整合） |
| B. 同日に成立する他吉神の宜を六黄道神の宜としても扱う | **原文の「從所宜」がこれに相当する（4章）** |
| C. 同日に成立する他凶神の忌を六黄道神の忌としても扱う | **原文の「從所忌」がこれに相当する（4章）** |
| D. 吉凶両方成立時の優先関係 | **原文に記述なし（11章）。推測で優先順位を作らない** |

**結論：COMPOSITE型は確定した（5神のみ）。** 六黄道神自身は固定の
宜/忌を持たず、その日に同時に成立している他の吉神・凶神の宜/忌を
そのまま反映する構造である。

## 4. 「從所宜」「從所忌」の意味

`docs/takujitsu_completion_audit.md`3章で確認した「COMPOSITE型が何を
意味するか原文で確認できなかった」という状態を、本フェーズで確定
できた。「六黒道」の対称的な定義文（1章）と比較すると、「與吉神併，
則從所宜」「與凶神併，則從所忌」という言い回しが六黄道・六黒道の両方に
共通して使われており、単発の言い回しではなく本書全体を通じた**安定した
慣用句**であることが確認できる。

文脈から判断すると：

- 「從所宜」＝「[併存する神殺の]宜とするところに從う」＝**その神殺の
  宜活動リストをそのまま採用する**、という意味に読むのが最も自然。
  「単にその日の吉凶（verdict）に従う」という抽象的な意味ではなく、
  「用事リストをコピーする」という具体的な意味に近い（4章冒頭の選択肢
  のうち1つ目）。
- 単数の吉神を想定しているのか複数の吉神が併存する場合に全ての宜を
  合算するのかは、原文からは明記されていない。ただし、擇日テキスト.pdf
  ・神殺象意.pdf全体を通じて「與〇〇併」という表現は他の箇所
  （小耗・觸水龍・四離四絶等）でも複数の神を「與『A』『B』併」と列挙
  する形式で使われており、**複数該当時に合算する（union）ことを禁止する
  記述は無い**。9章の設計ではunionとして扱うことを提案する（推測を
  最小化しつつ、既存のsource集約設計と整合させるため）。

## 9. COMPOSITE型の仮モデル設計（実装しない。設計のみ）

既存の`positiveMode`/`negativeMode`（"list"|"all_except"）とは性質が
異なる（"all_except"はActivityDefinition全件という**固定集合**からの
除外だが、COMPOSITEは**その日に動的に成立する他の神殺の宜/忌**という
**日ごとに変わる集合**を参照する）。型を無理に共用せず、新しい任意
フィールドを追加する案を提示する：

```ts
export interface ActivityProfile {
  // ...既存フィールド...

  /**
   * COMPOSITE型（六黄道等）。true の場合、この神殺は単独では宜/忌を
   * 持たず、同日に成立している他の吉神・凶神（kichijin/kyojinのみ。
   * 十二建除・二十八宿は対象外——原文が「神」と呼ぶ対象と一致させる）
   * の宜/忌をそのまま反映する。true のとき favorableActivityIds／
   * unfavorableActivityIds／positiveMode／negativeMode は無視する
   * （空のまま維持する）。
   */
  composite?: boolean;
}
```

評価側（`evaluateActivities()`）の想定アルゴリズム（2パス方式、実装は
しない）：

1. 通常どおり、COMPOSITE型ではない全ての吉神・凶神・十二建除・二十八宿
   から`RawContribution[]`を集計する（第1パス）。
2. その日に成立しているCOMPOSITE型の吉神（青龍等）ごとに、第1パスの
   `RawContribution[]`のうち**sourceType==="kichijin"または"kyojin"**
   （十二建除・二十八宿は対象外）だけを抽出し、その
   favorable/unfavorableの**和集合（union）**を、そのCOMPOSITE型神
   自身のsourceとして追加する（第2パス。circular参照を避けるため、
   COMPOSITE型自身のRawContributionは第1パスの対象外＝空のまま
   なので、他のCOMPOSITE型神を連鎖的にコピーすることはない）。
3. その日にCOMPOSITE型以外の吉神・凶神が1つも成立していなければ、
   何も追加しない（neutral）。原文に「該当が無い場合」の記述が無いため、
   推測で内容を作らない。

## 10. 二重計上の検討

例：三合が「裁衣」を宜とし、青龍（COMPOSITE）が同日成立する場合、
「裁衣」の`positiveSources`に**三合と青龍の両方を入れる**ことを推奨する
（9章の設計どおり）。理由：

- 原文は「[青龍が]從所宜」＝青龍自身がその宜を持つに至る、と明記して
  おり、青龍を単なる「補助情報」に格下げする根拠は無い。
- `computeVerdict()`は**存在の有無だけ**でverdictを決める（多数決では
  ない）ため、positiveSourcesが1件（三合のみ）でも2件（三合＋青龍）
  でも「裁衣」のverdictは変わらず`good`のまま——**source重複による
  判定変化は起こらない**（既存アーキテクチャがそのまま保証する）。
- 説明可能性の観点でも、「なぜ青龍がその日favorableな根拠を持つのか」
  をUIでそのまま辿れる（source.noteに「三合の宜に従う」等の由来を
  残せる）ため、二重計上ではなく正しい説明の重複であると判断する。

## 11. 吉凶同時成立時の扱い

原文（1・4章）には、六黄道神と吉神・凶神が**同時に**併存した場合の
優先関係の記述が無い（「與吉神併，則從所宜」「與凶神併，則從所忌」の
2文は独立した条件文であり、両方が同時に真になる場合の記述が無い）。

**結論：優先規則は存在しないと判断し、positive/negative双方を保持して
mixedとする**（9章の設計どおり、二重計上と同じ理由でpositive/negative
双方が自然に積み上がり、既存の`computeVerdict()`がそのまま`mixed`を
返す。新しい優先順位ロジックは設計にも含めていない）。

## 13. 結論・本番実装可能か

**原則として実装可能な設計案（9章）はできた**が、以下の理由により、
**本フェーズでは実装しない**（次フェーズの判断事項として持ち越す）：

1. **金匱の扱いが未確定**：5神と同じCOMPOSITE型にするのか、
   擇日テキスト.pdf由来のLIST型（家族会議・遠行）のまま残すのか、
   原典からは判断できない。ユーザー判断が必要。
2. **5神の現行LIST型データ（家族会議・遠行）を削除してCOMPOSITE型に
   完全に置き換えるか、削除せず保持するか**の判断。神殺象意.pdfの
   COMPOSITE定義に従うなら5神のfavorableActivityIdsは空にすべきだが、
   擇日テキスト.pdfという別の一次資料が明記した内容を削除してよいか
   （ここでも「成日」（前フェーズのCONFLICT）と同種の資料優先順位問題
   が生じている）はユーザー判断事項とする。
3. **COMPOSITE型の実装（評価アルゴリズムの2パス化）はevaluateActivities()
   のコア構造に手を入れる比較的大きな変更**であり、月破の徳神抑制
   （`docs/takujitsu_completion_audit.md`9章）と合わせて、クロス参照
   メカニズムの設計を一度にまとめて検討した方が手戻りが少ない可能性が
   ある。

（→ 14章のとおり、2026-09-10のユーザー確定を受けて本番実装した。
1と2はユーザー判断で解決。3は「必要最小限のフラグ1つ＋2パス」に留め、
月破の徳神抑制は別課題として切り離した。）
