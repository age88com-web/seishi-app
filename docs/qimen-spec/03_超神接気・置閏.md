# 03. 超神接気・置閏

## 目的

奇門遁甲の暦（二十四節気×三元×五日＝360日を一年とする）と、実際の太陽暦（365.2422日）のズレを補正すること。

## 実装状況（2026-09-15 時点）

**実装済み。** `src/lib/qimen/dingju.ts` の `resolveDingju()` が、天文学的な節入り瞬間ではなく
符頭の連続系列＋二至（冬至・夏至）の置閏判定で「今有効な節気パターン（`effectiveTerm`）」を
決定する。詳細な検証手順・全データは本章末尾および `tests/qimen_dingju_manreki.manual.ts` を参照。

### 実装で確定した事項（`docs/source/局数.pdf` と `docs/source/奇門遁甲万年暦.xlsx`（2018〜2020年実データ）による検証）

#### 1. 局数表は 72/72（24節気×上中下元）完全一致

`docs/source/局数.pdf`（書籍からの29頁抜粋）に、24節気×3元の局数表を裏付ける独立した記載が
2箇所（訂正された『統宗』の引用と、個別の数値列挙リスト）あり、両者は完全に一致する。
これと現行の `YANG_JU_TABLE`/`YIN_JU_TABLE` を照合し、3セル（雨水下元・霜降下元・小雪下元）の
誤りを修正済み（[02_定局.md](./02_定局.md) 参照）。以降は72/72完全一致。

#### 2. 節気の上元符頭は「前の節気の符頭+15日」の連続系列

`奇門遁甲万年暦.xlsx` の2018〜2020年・全72節気境界を全数検証した結果、節気から節気への
上元符頭日の間隔は、**置閏が起きた1箇所を除いて例外なく15日**だった（71/72が厳密に15日、
1箇所だけ30日＝置閏で1節気分15日が余分に挿入された）。

つまり局数の切り替えは「天文学的な節入り瞬間そのものを境界として節気名をそのまま
局数表へ渡す」方式ではなく、次のような連続系列である。

```
節気の上元符頭
  ↓ 15日間（上元5日・中元5日・下元5日）
次の節気の上元符頭
  ↓ 15日間
……
```

天文学的な節入り瞬間（`CalendarEngine` の `solarTermDateTime`）は、この符頭系列に対して
超神・接気としてズレる（下記）だけで、局数切り替えそのものの基準にはならない。

- **正授**: 符頭日＝節入り当日（`offset = 0`）。72件中3件（2019立冬・2019霜降・2020芒種）。
- **超神**: 符頭日が節入りより先行する（`offset = 節入り日 − 符頭日 > 0`）。72件中32件、
  範囲は+1〜+9日。
- **接気**: 符頭日が節入りより遅れる（`offset < 0`）。72件中38件、範囲は-1〜-7日。
- 3年分のデータでは同距離（タイ）となる事例は0件だった（未確認のまま。ただし本実装は
  「毎回最近傍を選び直す」方式を採らないため、タイブレークの問題自体が発生しない。後述）。

#### 3. 置閏は二至（冬至・夏至）への移行時にのみ判定する

> もし局の運行の最初から符頭までが夏至の9日以上前になる場合、ズレを修正するため閏を置く。
> （講義資料。冬至側も同じ「9日以上」の条件で運用されていることを実データで確認した）

判定式（`dingju.ts` の `stepSolsticeForward` に対応）:

```
candidate = 前の節気（大雪／芒種）の符頭 + 15日
offsetDays = 二至の実際の節入り日 − candidate
if offsetDays >= 9:
    直前の節気（冬至前=大雪／夏至前=芒種）の15日パターンをもう一巡させてから
    二至の符頭へ移行する（＝ candidate にさらに15日を足す）
```

奇門遁甲万年暦.xlsxの2018年実データで確認された唯一の置閏（大雪側）:

| 暦日 | 干支 | 内容 |
|---|---|---|
| 2018-11-28 | 甲子 | 大雪・本来の上元開始（置閏なしでの通常進行） |
| 2018-12-13 | 己卯 | **置閏**：大雪パターンの繰り返し・上元（陰4） |
| 2018-12-18 | 甲申 | 繰り返し・中元（陰7） |
| 2018-12-23 | 己丑 | 繰り返し・下元（陰1） |
| 2018-12-28 | 甲午 | 冬至・真の上元開始（陽1） |

このとき `candidate`（大雪符頭2018-11-28 + 15日 = 2018-12-13）に対し、実際の冬至の節入り
（2018-12-22 07:23）との差は **ちょうど9日**であり、「9日以上」の閾値に一致して置閏が発動する。
局数.pdf に記載されている芒種側の反復例（下記）も同じ規則（芒種の15日パターン＝陽6・3・9の
もう一巡）であることを確認済み。

> Ex）1975年6月22日己巳
> 6月17日甲子　符頭が夏至の前の超神
> 6月11日甲寅　符頭の10日前なので閏を入れる
> 15日の修正を入れる。（芒種）

（この例題自体は判読困難な断片だが、「芒種のパターンをもう一巡させる」という構造は、
`奇門遁甲万年暦.xlsx` で確認した大雪側の構造と同一であり、資料的根拠として採用した。）

#### 4. 天文節入り日と局数切替日は必ずしも一致しない

3.の連続系列と置閏規則により、ある日時が天文学的にどの節気に属するか
（`CalendarEngine` の `solarTerm`）と、局数表としてどの節気の行を参照すべきか
（`dingju.ts` の `effectiveTerm`）は、一般に一致しない。`奇門遁甲万年暦.xlsx` 全72節気境界の
うち、正授（一致）はわずか3件で、残り69件は超神または接気でずれている。

### 実装方式（stateless）

`resolveDingju()` は「前回計算した符頭」をモジュールのメモリ／グローバル変数として
保持しない純粋関数。呼び出しごとに、Excel実データで一意に確定できるアンカー地点
（2018年夏至の上元符頭 2018-06-16・己卯。理由は `dingju.ts` の `ANCHOR` 定数コメント参照）
から対象日時まで、二至（冬至・夏至）を単位とする半年ステップの符頭系列をその場で計算し直す。
同じ日時を渡せば、呼び出し順序や履歴に関係なく必ず同じ結果を返す。

### 検証（`奇門遁甲万年暦.xlsx` による回帰）

`tests/qimen_dingju_manreki.manual.ts`（fixture: `tests/fixtures/qimen_dingju_manreki.json`、
生成: `tests/fixtures/gen_qimen_dingju.py`）で、2018〜2020年の Excel 全244件（局数ラベル記載日、
Excel側の転記ミス9件を機械的に除外・1件は局数.pdfの確定値を優先）と `resolveDingju()` の
出力（陽遁/陰遁・局数）を比較し、**244/244（100%）一致**を確認済み。
